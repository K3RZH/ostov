# ostov-server

Слой: Layer0.

Сервер режима «сервер в локальной сети» (ADR-026): команды `Engine` по gRPC, только по TLS (СТ-33). Каждому вошедшему клиенту — свой экземпляр ядра со своим соединением с базой и своим пользователем; токен сессии — заголовок `authorization: Bearer`, сроки — `ostov_sec::Sessions` (30 минут / 12 часов). При первом запуске пустая база устанавливается, существующая доводится до конфигурации; сертификат `server.crt` создаётся сам, его раздают клиентам.

Синхронный драйвер PostgreSQL нельзя создавать и ронять в асинхронном потоке: всё, что ходит в базу, — через `spawn_blocking`, `Hub::start` тоже.

Запуск:

```
set OSTOV_DB_URL=host=localhost user=ostov password=… dbname=ostov
ostov-server --config config --listen 0.0.0.0:7700 --tls tls --host server.local
```

База — в `OSTOV_DB_URL` (пароль не виден в списке процессов): строка PostgreSQL или `sqlite:файл` для маленькой установки. Сертификат выписывается на `localhost`, `127.0.0.1`, имя компьютера и все `--host`; файл `tls/server.crt` кладут клиентам. Остановка — Ctrl+C.

Правила документов на Python — в сборке с фичей `python` (`cargo build -p ostov-server --features python`), Python рядом с программой (ADR-018).

## Внешние системы: сайт, CRM, другие программы (ИТ-12)

Подключаются так же, как приложение Ostov, — по тому же протоколу и с теми же проверками:

- **Протокол** — gRPC поверх TLS, описание в `crates/ostov-proto/proto/ostov/v1/engine.proto`. Клиенту нужен `tls/server.crt`. Версия протокола в ответе `Hello` должна совпадать с версией клиента (сейчас `3`).
- **Учётная запись** — своя у каждой системы. Администратор заводит её с ролью, где только нужные права: например, сайту — чтение товаров и создание заказов. `Login` возвращает токен, его передают в заголовке `authorization: Bearer <токен>`.
- **Данные меняются только командами** (`Save`, `Post`, `SaveBatch`), не записью в базу. Права, проверка остатков, проведение и журнал работают как для человека, в журнале видно, какая система что изменила.
- **Чтение для отчётов** — команда `Query` (SQL через платформу, с правами роли) или прямой доступ к базе только на чтение: описание таблиц и пример прав в PostgreSQL выдаёт `ostov schema`.
- **Под нагрузкой** запись, которую держит другая сессия, ядро повторяет само; если не вышло — ошибка `Unavailable`, её стоит повторить.

HTTP/JSON-шлюз к тем же командам — после первого выпуска.

Пока не сделано: пул соединений (каждая сессия держит своё), раздача корневого сертификата по ADR-021, запуск как службы.
