# Изменения

Версии по SemVer, до `1.0.0` каждая законченная веха поднимает вторую цифру. Версия протокола клиент ↔ сервер (`PROTOCOL_VERSION`) и формата конфигурации (`FORMAT_VERSION`) растут отдельно, только при потере совместимости.

## Не выпущено

Протокол `3`, формат конфигурации `1`.

### Добавлено
- `ostov-sql`: SQL через платформу — только `SELECT` по белому списку, имена метаданных, права на каждый объект, параметры `:имя`, `LIMIT` до 1000, оба диалекта.
- `Engine::query(sql, params)`: запрос `ostov-sql` с правами того, кто спрашивает, локально и через сервер (`rpc Query`). Деньги — `Decimal`, ссылки на справочники с названием, `posted` и `deleted` — `Bool`.
- `ctx.query(sql, **params)` в `on_post` на Python: чтение базы в транзакции проведения; `ostov.QueryError`. Для своих правил на Rust — `PostingRule::movements_reading` с `Reader`.
- Интерфейс: универсальный список объекта во вкладке, колонки из метаданных, загрузка окнами по 100 строк.
- `ListQuery.then_by`: сортировка списка по нескольким колонкам (`SortKey { field, descending }`) — в базе, со страницами и прыжками `seek`.
- `Engine::admin_journal_page`: записи журнала и ключ следующей страницы (`None` — записей больше нет). `admin_journal` остался и отдаёт только записи.
- `Connector::plan_local(path)` — план изменений базы под конфигурацию (СТ-50, К-6): новые таблицы, поля, ресурсы, пересоздание пустого регистра или отказ с причиной; база не меняется.
- `Engine::trial_post(document, data)` — пробное проведение (К-19): движения и остатки «до и после» по затронутым ключам, база не меняется; только локально.
- Журнал запуска (К-21): `LocalEngine::with_trace` и `LocalConnector::with_trace` отдают события — команды с временем и итогом, запросы `ostov-sql` после перевода с параметрами и числом строк (и из `ctx.query`), вызовы правил проведения.
- `ostov schema [папка]` и `ostov_core::local::describe_schema` — описание таблиц и колонок базы для внешних отчётов и доступ только на чтение в PostgreSQL (СТ-58).
- CI на GitHub: fmt, clippy и тесты на Windows и Linux, тесты на PostgreSQL 17 и с Python, `cargo-deny` (уязвимости, лицензии, источники).

### Исправлено
- Одновременная работа (СТ-57): два прихода нового товара с двух сессий больше не дают «ошибку базы»; два новых документа одного вида не получают один номер; при одновременных расходах остаток не уходит в минус; документы со строками в разном порядке не ждут друг друга вечно (итоги блокируются в одном порядке); SQLite на сервере ждёт записи, а не отвечает «database is locked».
- Если данные держит другая транзакция, запись повторяется до трёх раз (НТ-Н3), потом — понятное «данные сейчас меняет другой пользователь» (`ErrorCode::Unavailable`), а не «ошибка базы».
- SQLite: кэш страниц 64 МБ — проведение на базе с 1 млн движений ×1,3–1,4 от пустой (было ×2,25), НТ-П14.
- Заполнение базы и первый прыжок по большому списку без квадратичного роста.
- Текст с символом кода 0 — ошибка проверки, а не ошибка базы PostgreSQL.
- `pulldown-cmark` 0.13.6 (RUSTSEC-2026-0433), `async-executor` 1.14.1 вместо отозванной версии.

### Сломалось
- Протокол `3`: старые клиент и сервер с новыми не работают, обновлять вместе.
- `ostov_sql::prepare` принимает `Param` вместо `ostov_store::Value`. Число рядом с денежным полем переводится в его единицы: целое — это целые рубли, а не копейки; лишние знаки после запятой — ошибка.
- В `ostov-sql` сравнение сумм с разным числом знаков после запятой — ошибка.
- В `ListQuery` новое поле `then_by`: литералы без `..Default::default()` надо дополнить.
- Ключи страниц списка в новом формате: ключ, полученный до обновления, не подойдёт — список читается заново с начала.
- `StoreError::Busy` — новый вариант: `match` без `_` надо дополнить.
- Номера документов выдаёт счётчик `ostov_numbers` (старые базы получают его при открытии и продолжают с наибольшего номера): номер больше не возвращается к освободившемуся после удаления последнего документа.
- `post_to`, `save_to` и `insert_and_post_to` передают правилу ещё и соединение с базой: `|db, doc| …`.

## 0.6.0 — 09.11.2026

Протокол `2`, формат конфигурации `1`.

### Добавлено
- Интерфейс работает на ядре без демо-данных: выбор и создание базы, вход, меню из метаданных, пользователи и роли, документы во вкладках.
- `Connector::check_local`: проверка файла базы без записи в него.
- `Meta.registers`: регистры с измерениями и ресурсами для отчётов; `Meta.roles` с заголовками ролей.
- `SessionInfo.system`: системные права роли того, кто вошёл.
- `ListQuery.filter`: точный отбор по полям (текст без учёта регистра, пустое значение, ссылка по id).
- `Engine::admin_set_user_password`: администратор меняет пароль пользователю; на сервере сессии этого пользователя закрываются.
- Клиент при подключении сверяет версию протокола с сервером.

### Исправлено
- `create_local` не оставляет на диске базу без администратора, если его не удалось создать.
- `open_local` не дописывает таблицы в базу другой конфигурации.
- Первым пользователем можно добавить только роль с правом администрирования.
- Пароли не попадают в `Debug` (`NewAdmin`, `NewUser`, сообщения протокола с паролем).
- `server.key` создаётся с правами `600` на Linux.
- Тесты PostgreSQL без `OSTOV_PG_URL` помечаются как пропущенные, а не как пройденные.

### Сломалось
- Протокол `2`: старые клиент и сервер с новыми не работают, обновлять вместе.
- `Meta.roles` — `Vec<RoleInfo>` вместо `Vec<String>`.
- В строках списка `posted` и `deleted` — `Value::Bool` вместо `Int` 0/1.
- В `ListQuery` новое поле `filter`: литералы без `..Default::default()` надо дополнить.
- База хранит имя конфигурации (`name`) и отдельно название (`title`). Старые базы открываются и дописываются сами; базу другой конфигурации ядро не открывает.
