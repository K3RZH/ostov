# Изменения

Версии по SemVer, до `1.0.0` каждая законченная веха поднимает вторую цифру. Стадии: `-alpha`, затем `-beta`, релиз без суффикса; с 0.6.0 выпуски — альфа (теги `v0.6.0-alpha`, `v0.7.0-alpha`). Версия протокола клиент ↔ сервер (`PROTOCOL_VERSION`) и формата конфигурации (`FORMAT_VERSION`) растут отдельно, только при потере совместимости.

## Не выпущено

### Добавлено
- Пул соединений сервера: команда сессии берёт соединение на время выполнения и отдаёт; по умолчанию 10 на все сессии, `--db-connections <число>`. Раньше каждая сессия держала своё соединение, и сотня пользователей упиралась в предел PostgreSQL. `ostov_core::Pool`, `LocalEngine::pooled`, `Base::with_connections`.
- Себестоимость скользящей средней (СТ-К10, ADR-042): `AccumulationRegister::with_cost(Cost { qty, sum, by })`. У расхода без суммы ядро считает её само: сумма остатка × количество ÷ остаток на конец дня документа, по измерениям `by` (без партии), округление до копейки один раз на сумме; весь остаток уходит со всей суммой (СТ-К15). Остаток в минус не уходит (СТ-23). Приход, под которым товар уже списан более поздним расходом, нельзя добавить задним числом, изменить или отменить — «сначала отмените более поздний расход» (СТ-53); новый приход в день расхода считается после него. `Decimal::checked_mul_div`. Ключ `cost:` в YAML регистра — следующим шагом в `ostov-meta`.
- Свойства пользователя (ADR-043): `ostov_model::Config.user_fields` (`UserFieldDef { field, many }`) → `Meta.user_fields`; значения хранит ядро (`ostov_user_fields`), задаёт и читает администратор: `Engine::admin_user_fields(login)` (ссылки с названиями) и `admin_set_user_fields(login, fields)` — меняются только переданные свойства, пустой список очищает; проверка типа, «только одно значение» без `many`, ссылка только на существующий элемент справочника, запись в журнал. Через сервер — `rpc AdminUserFields` и `AdminSetUserFields`; протокол остаётся `3` (добавление совместимо). Ключ в YAML — следующим шагом в `ostov-meta`.
- Ограничения по записям (СТ-52, ADR-043): `RoleDef.restrictions` — `Restriction { object, field, user_field }`, роли видно только то, где поле объекта (у регистра — измерение) среди значений свойства пользователя; несколько ограничений действуют вместе, пустое свойство — не видно ничего, `admin` без ограничений. Действуют в списках и прыжках (`IN` в запросе к базе, со страницами и вехами), карточке, проведении и отмене, записи и пачке (записать можно только то, что потом увидишь; чужое — «нет записи»), пробном проведении и отчётах по регистру. Запросы `ostov-sql` к ограниченному справочнику или документу и к регистру с ограничениями для роли закрыты, пока перевод запроса не умеет отбор по записям. Конфигурация проверяется при загрузке: объект, поле и свойство того же типа. Ключ в YAML роли — следующим шагом в `ostov-meta`.
- Корневой центр сервера (ADR-021): при первом запуске сервер создаёт `tls/ca.crt` и `tls/ca.key`, сертификат сервера подписан этим центром; клиентам раздают `ca.crt`. Новое имя или адрес в `--host` — сертификат сервера выпускается заново на старые и новые имена, клиентам ничего менять не нужно (раньше новое имя молча не попадало в сертификат). В `server.crt` — цепочка с центром, так что клиент, которому дали его, тоже подключится. Старая установка без `ca.key` работает со своим `server.crt` как раньше. `Tls.ca_pem`, `CA_FILE`.
- Тайм-аут запроса (СТ-51): по умолчанию 30 с, на сервере `--query-timeout <секунд>`; дольше — запрос прерывается, пользователь видит «Запрос шёл слишком долго и прерван. Сузьте отбор или период.», соединение работает дальше. `Driver::set_query_timeout`, `StoreError::Timeout`.
- Ключи YAML для себестоимости, свойств пользователя и ограничений (ADR-042, ADR-043): `cost: { qty, sum, by }` у регистра → `RegisterDef.cost`, `user_fields` в `ostov.yaml` → `Config.user_fields`, `restrictions` в роли (`object`, `where: [{ field, in: user.<свойство> }]`) → `RoleDef.restrictions`. `ostov check` проверяет их с файлом и строкой и выводит предупреждение ADR-044: роль создаёт документ, но не читает справочник его обязательного поля (`ostov_meta::warnings`, `load_with_warnings`). Тип `Cost` теперь в `ostov-model`, `ostov_core::Cost` его переэкспортирует. В `config/` у «Склада» свойство «Склады» и ограничения кладовщика на расход и остатки. Формат конфигурации остаётся `1`: ключи необязательные, старые папки читаются. Кладовщик «Склада» без заданного свойства «Склады» не видит расходы и остатки и не может записать расход.
- `Config.positions`: файл, строка и столбец каждого элемента конфигурации по ключу (`catalog:goods/field:name`, `document:receipt/table:lines/field:qty`…), путь относительно папки конфигурации. Для конфигуратора R1 (ADR-013).
- Постоянные коды ошибок и предупреждений `ostov check` (`E001`…, `W001`), список в `crates/ostov-meta/README.md`; `Error.code`, `Error::is_warning`.
- Ограничения по записям в `ostov-sql` (СТ-52): `prepare(…, can_read, within, dialect)`; `within(объект)` даёт поля и значения, перевод добавляет `поле IN (…)` параметрами к каждому источнику (первый — в WHERE, присоединённые — в ON, табличная часть — по шапке документа), пустой список значений — `1 = 0`. `ostov_sql::Limits`.
- `ostov-py` находит стандартную библиотеку Python в Linux и macOS (`lib/python3.<N>`); в CI задача `python-linux` на ubuntu-24.04.

### Сломалось
- `ostov check` печатает `файл:строка: КОД текст` вместо `файл:строка — текст`; `ostov_meta::Error::new` принимает код.
- `ostov_sql::prepare` принимает `within`; регистры теперь проверяются через `can_read`, как справочники и документы.

### Исправлено
- `Connector::plan_local` работает и при открытой базе: план только читает и замок базы не берёт. Конфигуратор проверяет новую конфигурацию, не закрывая базу (К-16): план, потом закрыть движок и открыть с новой конфигурацией.

## 0.7.0-alpha — 16.11.2026

Протокол `3`, формат конфигурации `1`.

### Добавлено
- `ostov-sql`: SQL через платформу — только `SELECT` по белому списку, имена метаданных, права на каждый объект, параметры `:имя`, `LIMIT` до 1000, оба диалекта.
- `Engine::query(sql, params)`: запрос `ostov-sql` с правами того, кто спрашивает, локально и через сервер (`rpc Query`). Деньги — `Decimal`, ссылки на справочники с названием, `posted` и `deleted` — `Bool`.
- `ctx.query(sql, **params)` в `on_post` на Python: чтение базы в транзакции проведения; `ostov.QueryError`. Для своих правил на Rust — `PostingRule::movements_reading` с `Reader`.
- Интерфейс: универсальный список объекта во вкладке, колонки из метаданных, загрузка окнами по 100 строк.
- `ListQuery.then_by`: сортировка списка по нескольким колонкам (`SortKey { field, descending }`) — в базе, со страницами и прыжками `seek`.
- `Engine::admin_journal_page`: записи журнала и ключ следующей страницы (`None` — записей больше нет). `admin_journal` остался и отдаёт только записи.
- `Connector::plan_local(path)` — план изменений базы под конфигурацию (СТ-50, К-6): новые таблицы, поля, ресурсы, пересоздание пустого регистра или отказ с причиной; база не меняется.
- `Engine::trial_post(document, data)` — пробное проведение (К-19): движения и остатки «до и после» по затронутым ключам, база не меняется; только локально.
- Нагрузочный прогон НТ-Н3 (`ostov-client/tests/load.rs`, `--ignored`): десять клиентов через сервер — проведение, списки, отчёт; проверка, что записи не теряются и остатки сходятся.
- Журнал запуска (К-21): `LocalEngine::with_trace` и `LocalConnector::with_trace` отдают события — команды с временем и итогом, запросы `ostov-sql` после перевода с параметрами и числом строк (и из `ctx.query`), вызовы правил проведения.
- `ostov schema [папка]` и `ostov_core::local::describe_schema` — описание таблиц и колонок базы для внешних отчётов и доступ только на чтение в PostgreSQL (СТ-58).
- CI на GitHub: fmt, clippy и тесты на Windows и Linux, тесты на PostgreSQL 17 и с Python, `cargo-deny` (уязвимости, лицензии, источники).

### Исправлено
- Одновременная работа (СТ-57): два прихода нового товара с двух сессий больше не дают «ошибку базы»; два новых документа одного вида не получают один номер; при одновременных расходах остаток не уходит в минус; документы со строками в разном порядке не ждут друг друга вечно (итоги блокируются в одном порядке); SQLite на сервере ждёт записи, а не отвечает «database is locked».
- Сервер на SQLite под нагрузкой: вход проверяет пароль (Argon2) вне транзакции записи, а транзакции записи одной базы внутри процесса идут строго по очереди — сессия больше не «голодает» под непрерывной записью других (найдено нагрузочным тестом НТ-Н3).
- Если данные держит другая транзакция, запись повторяется до трёх раз (НТ-Н3), потом — понятное «данные сейчас меняет другой пользователь» (`ErrorCode::Unavailable`), а не «ошибка базы».
- SQLite: кэш страниц 64 МБ — проведение на базе с 1 млн движений ×1,3–1,4 от пустой (было ×2,25), НТ-П14.
- Заполнение базы и первый прыжок по большому списку без квадратичного роста.
- Текст с символом кода 0 — ошибка проверки, а не ошибка базы PostgreSQL.
- `pulldown-cmark` 0.13.6 (RUSTSEC-2026-0433), `async-executor` 1.14.1 вместо отозванной версии.

### Сломалось
- Протокол `3`: старые клиент и сервер с новыми не работают, обновлять вместе.
- `ostov_sql::prepare` принимает `Param` вместо `ostov_store::Value`. Число рядом с денежным полем переводится в его единицы: целое — это целые рубли, а не копейки; лишние знаки после запятой — ошибка.
- В `ostov-sql` сравнение сумм с разным числом знаков после запятой — ошибка.
- В `ListQuery` новое поле `then_by`: литералы без `..Default::default()` надо дополнить.
- Ключи страниц списка в новом формате: ключ, полученный до обновления, не подойдёт — список читается заново с начала.
- `StoreError::Busy` — новый вариант: `match` без `_` надо дополнить.
- Номера документов выдаёт счётчик `ostov_numbers` (старые базы получают его при открытии и продолжают с наибольшего номера): номер больше не возвращается к освободившемуся после удаления последнего документа.
- `post_to`, `save_to` и `insert_and_post_to` передают правилу ещё и соединение с базой: `|db, doc| …`.

## 0.6.0-alpha — 09.11.2026

Протокол `2`, формат конфигурации `1`.

### Добавлено
- Интерфейс работает на ядре без демо-данных: выбор и создание базы, вход, меню из метаданных, пользователи и роли, документы во вкладках.
- `Connector::check_local`: проверка файла базы без записи в него.
- `Meta.registers`: регистры с измерениями и ресурсами для отчётов; `Meta.roles` с заголовками ролей.
- `SessionInfo.system`: системные права роли того, кто вошёл.
- `ListQuery.filter`: точный отбор по полям (текст без учёта регистра, пустое значение, ссылка по id).
- `Engine::admin_set_user_password`: администратор меняет пароль пользователю; на сервере сессии этого пользователя закрываются.
- Клиент при подключении сверяет версию протокола с сервером.

### Исправлено
- `create_local` не оставляет на диске базу без администратора, если его не удалось создать.
- `open_local` не дописывает таблицы в базу другой конфигурации.
- Первым пользователем можно добавить только роль с правом администрирования.
- Пароли не попадают в `Debug` (`NewAdmin`, `NewUser`, сообщения протокола с паролем).
- `server.key` создаётся с правами `600` на Linux.
- Тесты PostgreSQL без `OSTOV_PG_URL` помечаются как пропущенные, а не как пройденные.

### Сломалось
- Протокол `2`: старые клиент и сервер с новыми не работают, обновлять вместе.
- `Meta.roles` — `Vec<RoleInfo>` вместо `Vec<String>`.
- В строках списка `posted` и `deleted` — `Value::Bool` вместо `Int` 0/1.
- В `ListQuery` новое поле `filter`: литералы без `..Default::default()` надо дополнить.
- База хранит имя конфигурации (`name`) и отдельно название (`title`). Старые базы открываются и дописываются сами; базу другой конфигурации ядро не открывает.
